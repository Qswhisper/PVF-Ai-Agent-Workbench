# 复杂副本机制壳与内容移植只读核查

状态：默认可用

用途：处理塔、事件、竞技或其他特殊副本的移植、换皮、入口替换与机制复用。把“运行机制壳”“战斗内容”“显示身份”分开审计，不保存某个成品的楼层数、地图 ID、APC ID 或当前数值。

## 三层拆分

| 层 | 主要证据 | 不能据此证明 |
| --- | --- | --- |
| 运行机制壳 | registry 身份、`.dgn` 副本类型、起始/结束地图、活动层表、难度/修正表、复活与特殊规则字段 | 显示名称相同、字段可解析，不等于运行规则相同或字段一定生效 |
| 战斗内容 | 活动 `.map`、刷怪/APC、波次、对白、奖励、门票和地图反向归属 | 文件仍留在 PVF，不等于它仍处于活动路线 |
| 显示身份 | 名称说明、worldmap/WDM/UI 按钮、封面、坐标、连线和客户端资源 | UI 可见或坐标正确，不等于能进图、能逐层推进或资源完整 |

## 执行

1. 用户给自然语言副本名时先走 dungeon `SearchName`。同一显示名返回多个已登记 `.dgn` 时全部保留，不能挑一个熟悉路径当作唯一身份。
2. 对官方参考、目标成品和实机记录分别记证据层；两份 PVF 记录完整 SHA256。相同 ID、路径或名称不能替代双方独立读回。
3. 完整读取每个候选 `.dgn`，分别记录机制壳字段、活动地图/层结构、难度或修正表、复活字段、奖励/门票和显示字段。活动计数之外残留的对白、地图或旧结构只能标为残留候选。
4. 闭合活动 `.dgn -> .map -> .til -> .img`、map 对 dungeon 的反向归属、monster/APC registry，以及 worldmap/WDM/UI 入口。相同相对路径仍需比对实际内容；PVF 引用不证明客户端资源存在。
5. 已有实机通过的机制壳可以作为移植基线，但这是目标版本的工程证据，不是“补一个副本类型标签即可获得同样玩法”的通用公式。
6. 先验证机制壳能完成完整循环，再逐批替换战斗内容和显示身份；每轮只引入一个主要变量。出现黑屏、卡层、重复召唤或入口错线时，应能回到上一轮唯一变化定位。
7. 起始房间/第一阶段与后续房间分开验证。历史目标曾出现起始阶段未采用后续阶段同一修正表的实机负例；这证明必须分段测，不证明所有塔或所有版本都有首层例外。
8. 可解析的普通字段可能被特殊机制壳覆盖。历史目标曾出现复活字段静态存在、死亡后仍不能复活的实机负例；遇到这种情况先判定机制族，不继续堆叠同类字段。
9. 血战/祭坛类机制若存在 `[blood phase time]` 及相邻 phase/group 表，先把整组视为机制壳。历史同一目标 lineage 多次报告仅改该表末列后启动失败；当前目标与官方参考静态同形只证明结构存在。没有当前版本单变量复现前，不命名列义、不把末列当普通时间或倍率入口，也不跨行宽替换。
10. 将 monster 波次替换或混入独立 `[ai character]` 块时，先只改一个房间并把 APC 作为清层计数风险单列。一个历史交接记录称起始房残留 APC 块曾造成死亡计数异常和门不开，删除后卡关解除；由于缺少同轮原始观察表，只保留为目标版本风险。实机分别记录击杀计数、门开启、清层推进和正常退出，不能从静态 APC 存在推断会计入同一波次。

## 实机矩阵

- 入口显示、点击、进图、退出、重进和完整结算。
- 起始房间/第一阶段、一个中间阶段和结束阶段分别记录敌我强度、推进与清层。
- 死亡、复活、门票、次数、奖励和失败后的行为分别验证。
- 固定首发 APC 检查持续状态是否被再次关闭、召唤是否重复、首发链是否只执行一次。
- 地面/墙面、封面、头像、对白、坐标、连线和其他客户端资源单独做可见性检查。

## 停止条件

- 同名 registry 身份、活动路线、修正表列义或 map 反向归属仍未闭合。
- 第一阶段与后续阶段表现不同但尚未定位到个体、地图或全局表。
- `[blood phase time]` 或相邻 phase/group 表的列义仍靠历史猜测，或修改后启动失败形态尚未区分。
- PVF 静态正确但客户端资源、复活、逐层推进或结算没有实机证明。
- 方案需要同时改变机制壳、地图、APC、难度、UI 和中文等文字，无法做单变量归因。
