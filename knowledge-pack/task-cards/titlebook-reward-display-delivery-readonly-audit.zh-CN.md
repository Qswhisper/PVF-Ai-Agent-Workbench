# 称号簿奖励发放与展示闭合只读核查

状态：默认可用

## 先读

- `safety/README.zh-CN.md`
- `dictionaries/quest-drop-reward-ticket-fields.zh-CN.md`
- `task-cards/client-assets-imagepacks-ui-readonly-audit.zh-CN.md`
- `task-cards/text-stringlink-encoding-readonly-audit.zh-CN.md`

## 适用

用于核查目标 PVF 的 `etc/titlebook.etc` 中，一个称号簿分区或特殊成就显示什么、实际发放什么，以及两者是否闭合。它不把称号簿分区名当成任务名，也不授权修改 StringLink、客户端 IMG/NPK 或客户端文件。

## 执行

1. 直接读取目标 PVF 的 `etc/titlebook.etc`。若用户给出的是称号簿分区名而任务名称搜索零命中，不据此判定内容不存在，也不转为全包正文盲搜。
2. 先区分 `[section]` 容器和 `[title collection info]` 槽位表。槽位表中的数字只在目标版本证据闭合后解释；不要把项目槽位、任务 ID 或奖励 ID 复制成跨版本事实。
3. 以当前槽位表实际引用的任务为活跃链入口，再闭合 `槽位 -> quest registry -> .qst -> reward equipment/stackable`。已登记且结构完整的旧任务可以与替代任务并存；registry 成员身份不证明当前称号簿槽位仍在使用它。
4. 重复审计至少按五个维度分别建键：活跃槽位、任务 ID、称号或奖励身份、绑定副本、条件与奖励语义。相同文案或相同副本只能形成候选，不能直接判重复；相同文案闭合到不同任务或条件，或者同一任务/称号被多个活跃槽位引用时，标记为待复核。已登记但未被活跃槽引用的旧链单独报告，不计入当前重复。
5. 槽位重排前从当前目标的 section/slot 结构推导分组边界，并检查每组活跃项是否构成连续前缀、空位是否只在尾部。历史目标客户端曾出现“遇首个空槽便不再显示其后槽位”、压实后恢复的实机负例；这是版本风险，不是固定槽数公式。不得硬编码分组数或每组宽度，修改后逐类检查空槽之后的后续项仍可见。
6. 在目标 `[section]` 内，用完整 `[section name]` token 定位对应的 `[reward type]`。同名或同构块重复时，必须保留外层 section 与相邻上下文，不能只靠一个短名称替换。
7. 对同一个 `[reward type]` 分开记录三类证据：
   - 展示名：`[name]`；
   - 展示资源：`[image path]` 的客户端 IMG 路径与帧索引；
   - 实际结果：`[send postal]`、属性奖励、`[give emotion]` 或目标中观察到的其他效果字段。
8. `[send postal]` 中的物品数字按目标字段上下文闭合到正确的 `stackable` 或 `equipment` registry，并读取实际物品；不要凭数字大小、名称或图片路径猜类型。邮件正文存在不证明物品成功到达。
9. `[image path]` 是客户端显示资源引用，不是物品 registry。分别核查脚本路径、帧索引和对应客户端资源；PVF 中有路径不证明客户端实际显示正确。
10. 修改方案必须同时审阅“实际结果、展示名、展示资源”。只改变 `[send postal]` 不会自动同步 `[name]` 或 `[image path]`；历史目标实机已出现“邮件发对、称号簿仍显示旧奖励”的失败形态。
11. 只读结果中若 `[name]` 或其他文字是 StringLink，保留该表示并按 StringLink 边界处理；不能把另一版本的内联 Cn/Tw token 当作可直接替换证据。
12. 若任务包含称号/成就平衡，分开核查获取负担、目标玩法节奏和奖励的实际效果字段，再与目标版本的正确属性池比较。说明文字、相邻多列数字和未确认提案都不能代替效果块；把“设计方案、静态落地、实机结果”分成三种状态记录，不能据方案或读回宣布平衡已验证。

## 验收

- 能指出目标分区所属的 `[section]` 与完整 `[reward type]` 边界。
- 能分别列出实际发放/效果、展示名、IMG 路径与帧索引，且不把它们合并成一个字段。
- 重复报告已区分槽位重复、任务重复、称号/奖励重复和语义近似；没有把同文案或同副本直接写成重复事实。
- 槽位重排已按目标结构检查连续活跃前缀，并把空槽后的客户端可见性列为必测项；没有硬编码其他版本的槽位宽度或分类数量。
- 邮件物品 ID 已通过目标 registry 解析，图片路径没有被误当作物品身份。
- 若用户要求改奖励，方案明确包含邮件收取、奖励内容、称号簿名称和图标的客户端 smoke；静态读回不写成实机成功。
- 没有保留某个项目的成就名、物品 ID、图片帧或槽位号作为通用默认值。
- 平衡结论已区分获取负担、玩法节奏、实际效果以及方案/静态/实机三层证据；没有从说明文字或拼接多列数字推断奖励强度。
- 不生成输出 PVF，不改客户端，不修改 NPK/IMG。

## 运行边界

静态只读只能证明三类字段在目标块中存在以及 registry/资源引用是否可闭合。它不能证明称号簿进度会触发、邮件会投递、背包能接收、名称与图标实际渲染、图片帧正确或奖励效果可用；这些仍需目标客户端实机验证。
