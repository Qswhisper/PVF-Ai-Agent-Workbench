# 安全边界

状态：默认可用

## 总规则

- 默认只读。
- 生成阶段不覆盖输入 PVF；若输入路径就是已配置的测试客户端 `Script.pvf`，只有其内容寻址备份已核对并成为受保护锚点后，单独授权的客户端部署才可替换该实时路径。
- 不默认修改客户端资源。
- 不把真实 PVF、客户端、API key、索引缓存或运行产物放进 Workbench。
- 数字 ID 不是事实，必须按上下文通过正确 `.lst` registry 解析。
- 教程示例 ID、社区注释、GM 字段、源码字段不能直接作为写 PVF 依据。
- 目标 PVF、任务选择器和工作台已经明确时，第一条 shell 动作必须是路由给出的 `workbench.bat` 命令。不要用 `Test-Path`、`Get-Item`、`Get-ChildItem`、`Resolve-Path` 预检工作台、目标 PVF 或报告/输出目录，也不要用分号串联检查；工作台命令会自行校验输入并创建其声明的外部输出目录，失败后再按返回错误诊断。
- 用户要求完整 SHA256、要求源 PVF 保持不变、要求最后确认源文件没有变化，或要求其他修改前后身份依据时，任务规定的第一条工作台命令仍保持不变，紧接着的第二条工作台命令必须是一次 `pvf-read fingerprint`，并且早于任何 `pvf-change`。多份 PVF 在同一命令中重复 `--pvf`；基线只做一次，全部成品读回后再原样运行一次并逐项比较 `sourcePvfSha256`。不要拖到 validate、预演或正式生成前才首次执行：晚到的第一次指纹无法倒推修改流程开始前的状态。不要改用通用哈希命令、帮助或 adapter-info。普通读取默认不承担整份大 PVF 的哈希开销。

## 面向新手的说明

- 安全检查、哈希绑定和机器清单全部保留，但用户可见回复先用通俗中文说明“能否继续、会改什么、风险是什么、下一步做什么”。
- 主结论优先说“预演（先检查；中文改动会用临时文件验证并立即清理）”“生成独立 PVF”“生成后复查”“普通脚本里的完整中文名称/描述（包括多行）可验证修改；批量需先核对准确数量”，不要在开头堆叠 ASCII、non-ASCII、backend、manifest、approval code、readback 或 smoke check。
- 用户确实需要命令、路径、确认码、错误码或实现细节时，放到“技术详情（通常不用看）”之后。不得为了通俗而省略阻断条件或安全步骤。

## 写 PVF 必须满足

1. 明确目标 PVF。
2. 对同一源 PVF 和同一 change-set 完成未阻塞 dry-run，保留 `DRY-RUN-MANIFEST.json` 和 approval code。只要预演被阻止，命令输出和核验记录内部都不会提供可用许可，不要从绑定哈希推算或尝试生成。
3. apply 时显式提供该 dry-run manifest 和 approval code；源 PVF 或 change-set 哈希变化后必须重新 dry-run。
4. 明确输出 PVF，且输出路径不是源 PVF。
5. 创建按源文件 SHA256 存放并核对的备份；相同源版本只保留一份，复用前再次核对哈希。
6. 解析相关 `.lst`。
7. 做最小修改。
8. 保存到显式输出。
9. 重新打开输出 PVF 读回。
10. 生成 manifest 或等价变更清单。
11. 需要时由用户做游戏内验证。

多轮迭代不是自动累积。下一轮只包含本轮差异时，必须在 change-set 中用 `baseline.applyManifest` 显式引用上一轮成功的 `APPLY-MANIFEST.json`。工作台核对上一轮输出、最初受保护源和完整哈希后，以上一轮输出作为本轮输入；`target.sourcePvf` 和 profile 仍指向最初受保护源。预演时按 `pvf-change validate` 返回的 `agentHandoff.nextCommandOnly` 原样执行，不要自行补一个指向最初源的 `--pvf`。未声明该字段就仍表示“原始源 + 本轮改动”，不得部署到已经含历史改动的客户端。部署预览优先核对客户端当前版本与本轮输入版本；若客户端命中更早的累计祖先，只有逐级验证每份 `previousApplyManifest` 文件及 SHA256、相邻输入输出 SHA256、受保护源锚点/来源和连续 chainDepth 后，才允许一次性快进到最终输出。缺清单、哈希漂移、循环或客户端不在该线性链上时默认停止；这不等于主动切换修改分支。

“受保护源”保护的是一份完整、不可变的内容，不强制原始路径永远不动。正式生成会先把最初版本保存为按 SHA256 命名并重新核对的外部备份；该备份随后成为受保护源锚点。若最初输入正是 profile 测试客户端里的 `Script.pvf`，生成阶段仍不覆盖它，但单独授权的 `client-pvf` 部署可在确认客户端关闭后自动安装独立成品。用户不需要手工复制文件。下一轮仍使用 `baseline.applyManifest`；工作台会从核验记录中找到受保护锚点，不会把客户端里已经部署的版本误当成最初基座。

## 新增块 / 新增文件护栏

- 新增标签块、新增完整 `.stk` / `.qst` / `.dgn` 等文件，或跨系统引用新 ID 时，先在目标 PVF 的同目录、同扩展名、同用途样本中找最近邻对照。
- 最近邻对照默认只做窄范围抽样，不做无必要全库扫描。优先读目标 PVF 中 3 个左右同类样本，确认块位置、是否有闭合标签、列数、tab、空列和配套字段。
- 已有字段的单个数字最小替换可以按目标块 readback 处理；新增块和新增文件不得凭字段名想象格式。
- 如果目标 PVF 没有同类样本，外部教程、工具源码或其他 PVF 只能作为候选线索，必须提高风险等级并安排 readback / 实机验证。
- 搜索工具返回 0 命中不能单独证明标签不存在，尤其是大规模全文搜索。遇到关键标签时，用目标目录、已知样本路径或其他搜索通道复核。
- 新增 `.wdm`、`.co`、`.lst`、`.nut`、`.sqr`、`.str` 不再是能力级“永远不能做”，但也不属于普通 `write-file`：必须在 change-set 中提交匹配的 `writeProof`，由工作台对目标格式、目标路径冲突、脚本结构、临时写出或编码往返和独立读回重新核验。缺证据或任一核验失败仍保持阻断。已有 `.co/.lst/.nut/.sqr/.str` 的普通修改继续阻断；已有 `.lst` 只有明确的 `registry-lifecycle` 新增行并通过冲突/引用闭合检查才可进入专用路线。已有 `.nut` 只有 `existing-nut-controlled-edit` 专用路线可修改：目标必须位于 `sqr/`，全部替换只包含数字、英文和常见符号，所有同路径变化使用相同证明，并闭合完整原文 SHA256、既有 load_state/passive/appendage 加载链或任务卡定义的显式 direct-character-state 同职业登记或 direct-character-skill-use 既有技能使用前后公共回调登记，或任务卡定义的 direct-character-skill-proc 同职业公共函数、无条件调度调用、技能状态、头文件编号及技能登记证据闭合、函数结构、内置与目标 API 证据、APID 全 `sqr/` 冲突搜索、临时独立 PVF 往返和最终独立读回。加载链目标路径必须位于真实函数调用参数中，不能只出现在注释、与调用无关的孤立字符串或带可执行前缀的行尾注释里。写入时不得重新编码整份 NUT，只能把精确文字位置映射到唯一原始 ASCII 字节区间，并证明其余原始字节逐段完全不变；临时输出和最终输出重新打开后还必须由独立解析器核对脚本原始字节 SHA256。既有不可还原 Cn/Tw 旧字节可原样保留，但替换内容触及中文等文字、位置不唯一或保留字节漂移仍会停止。静态通过仍必须实机验证异常状态、时序、刷新/叠加与普通受击边界。已有 `.wdm` 中只包含数字、英文和常见符号的既有字段仍可走原始 token 最小预演。
- 目标 PVF 内已有普通文本文件可用 `copy-file` 复制到不存在的同扩展名路径。该路线绑定完整源文本 SHA256，预演时临时写出并独立读回后立即清理；不允许复制到源路径本身，不允许覆盖目标，也不允许复制上述受保护高风险类型。同一原子 change-set 可以精确修改其他既有路径的引用，例如复制正确的 `.til` 并同时切换现有 `.map`；只禁止在这一轮修改刚复制出来的目标本身，修改克隆内容才需要第一轮成功核验记录作为累计第二轮。复制不会自动授予登记表、客户端资源或未声明引用的改动权限。

- 新建/复制 `.map` 或修改其资源引用时，预演必须在最终原子方案上从源目录和目标目录分别重解析 `.map -> .til -> .img`。同一个相对 TIL token 因地图目录变化而命中不同内容时，必须报告前后实际路径、语义文本 SHA256、可得的原始内容 SHA256、IMG 引用和 `[img pos]` 差异，并停止生成许可。若同轮复制了正确 TIL，使目标最终内容与来源一致，可以通过静态闭合；客户端 IMG/NPK 完整性和地图实际绘制仍需另查与实机验证。
- `worldmap-lifecycle` 必须把新 `.wdm`、`worldmap/worldmap.lst` 行、`.wdm [ui path]`、`IDC_WORLDMAP_BUTTON*` 与 dungeon registry，以及至少一个 town gate 和 region-town 配套作为同一个原子预演；静态闭合通过仍不等于客户端显示或实机进图成功。
- 既有二进制 `.ani` 只有 `[DELAY]` 受控路线可修改：每个文件恰好一条替换，解析器必须消费全部原始字节，文本结构除数字 token 外完全一致，实际变化只能映射到既有 `[DELAY]` 的 4 字节有符号整数。写入不得重编码整份 ANI，只覆盖目标字段并证明所有非目标字节完全不变；预演必须临时生成独立 PVF 并以独立解析器核对完整文本和目标文件原始字节 SHA256，正式输出也必须重新核对原始字节 SHA256。其他字段、帧结构、路径、中文等文字、新增 ANI 和客户端 NPK/IMG/UI 继续阻断；静态通过后仍需实机验证动画时长和状态衔接。

## 文本与编码护栏

- 创建工作会话或 change-set 后，先确认源 PVF、输出 PVF 和客户端路径在记录中没有乱码。
- 普通 `Cn` 搜索、`.str`、StringLink 和含非 ASCII 的脚本读取由 Workbench 自动进行语义保护；不要要求新手手工切换 backend，也不要关闭该保护来换取速度。
- 含中文字符串或 StringLink 样 token 的 PVF 文本文件，不能只用“读回正常”判断客户端文本安全。
- 数字字段最小替换可按已验证安全路线处理：使用目标原文实际对应的 `pvfEncoding=Cn` 或 `pvfEncoding=Tw`，不做简繁转换，不自动转换 StringLink。两种编码冲突时不得把明显乱码当成源文件损坏。
- 整数与小数可以互改；选择器必须包含完整标签和精确原值，例如 `[attack damage rate]\r\n1` 到 `[attack damage rate]\r\n0.8`。禁止用裸 `1` 或裸 `0.8`，因为重复数字无法证明目标字段。
- 普通脚本中完整、明确的可见中文字段可以使用 `textWriteMode: "verified-inline-text"`。`previousText` 与 `newText` 必须都是完整反引号 token，token 内允许真实 CRLF/LF 多行，编码必须是目标确认的 `Cn` 或 `Tw`。单点替换默认要求恰好 1 次；相同完整文字重复时，可从同一次原始读回复制紧邻的 `contextBefore` 和/或 `contextAfter`，让“上下文 + 旧文字”只命中目标位置。若同构块连相邻上下文也完全相同，可给该块内的每条参数或文字变化增加 `scope: { startText, endText, expectedRanges }`，三个值都必须来自同一次原始读回。scope 只在精确且不重叠的区间内部计数；旧文字和相邻上下文都不能越界，开始/结束标记不能被改写，新文字不能注入标记，区间数量、位置和内容哈希会绑定预演与正式生成。任何缺失、重叠、数量或位置漂移都会停止。上下文和 scope 都只用于定位，不会放宽完整文字、字段、StringLink、文件类型或编码检查。不要使用容易随文件变化漂移的出现序号，也不要自行发明 `scopePart`。批量必须使用 `replaceAll=true` 并填写精确正整数 `expectedOccurrences`；有 scope 时在区间内计数，实际数量不一致就停止。旧字段为纯英文或空字符串时，它本身不能证明新中文该用哪种编码，必须由同一脚本中的已有中文提供证据，否则停止。旧的 `verified-inline-cn` 仅作为兼容别名接受。
- `.dgn` 的 `[tower dialog]` 不是通用标签白名单。只有严格结构 `[tower dialog]`、下一项为整数层号、再下一项为待改的完整反引号对话 token、其后紧跟完整事件 token `` `on start` `` 或 `` `on complete` `` 时，才把该对话认作可见消息并进入同一 `verified-inline-text` 临时往返。事件 token 本身、未知事件、缺失层号、部分中文、StringLink 或结构漂移仍停止；结构证据和 SHA256 进入写入证明。
- `.skl` 的备用说明字段按结构族准入，不再逐个写死标签：若即时父标签以 ` ex` 结尾，去掉该后缀后必须仍是工作台已经确认的可见文字标签。例如 `[explain ex]` 继承 `[explain]`、`[basic explain ex]` 继承 `[basic explain]`，以后同构的 `[skill explain ex]` 也会继承 `[skill explain]`。只允许完整反引号 token 使用 `verified-inline-text`，并继续要求目标确认的 `Cn`/`Tw`、精确命中数量、临时独立 PVF 往返和最终读回；结构族与基础标签进入写入证明。非 `.skl`、未知基础标签（如 `[logic explain ex]`）、部分 token、StringLink 或未计数重复仍停止。
- `etc/titlebook.etc` 的 `[section name]` 只作为该精确路径中的称号簿分区可见文字开放：只允许单行完整反引号 token，不能换行、不能包含 PVF 标签括号，其他 `.etc` 路径的同名标签仍停止；仍需目标确认的 `Cn`/`Tw`、精确命中、临时独立 PVF 往返、最终读回和客户端文字检查。
- `.qst` 的 `[condition data]` 只开放一种严格进度文字结构：闭合 `[condition data] ... [/condition data]` 内，父标签后第一项是整数，第二项是单行完整反引号进度 token，且 token 后下一项就是闭合标签。新旧文字必须保留原有 `%d` 等占位符数量和顺序，不能换行、不能包含 PVF 标签括号；其他 `.qst` 文字、StringLink、结构漂移或占位符变化仍停止。
- `etc/upgrade.etc` 与 `etc/amplifyupgrade.etc` 只通过 `upgrade-table-level-edit` 修改。`[table]` 固定按 17-token 原始组解析，B-R 只表示位置；新接口允许 `[table]` 与含 0 组的四值 `[amplification const]` 独立选取原始组，不推断游戏显示等级，新旧接口不得混用。复制/保留列须精确覆盖 B-R；`setCells` 须绑定精确旧数字且不得与复制重叠。修改上限须逐项声明六稀有度且源段完整；仅改表格时可在 `tableEdit` 路线省略 `maxLevelByRarity`，必须逐字保留唯一闭合的原上限段、绑定相等的前后哈希，不能补造缺失行。每个组件记录 changed/no-op 和写入需求，全 no-op 不授权生成。锻造仍排除；宽度、组、数字或临时/最终读回异常都停止，静态通过仍需实机验证。
- 参数/结构与中文联动时，必须拆成同一 `pvfPath` 下的独立变化：先用 `pvf-read read --raw`（或 `read-batch --raw`）取得与写入校验完全一致的原始 token 排列。未显式给编码时，原始读取会只读比较 Cn/Tw，并且只在一方明显更干净时自动选择；选择结果在 `textUsage.automaticEncodingSelection` 中公开，之后把该 `selectedEncoding` 填入完整中文变化的 `pvfEncoding`。参数块只包含数字、英文、标签、Tab 和常见符号；中文使用完整文字 token；若依赖同一个精确区间，每条变化都声明相同的 scope。普通读取仅用于查看，可能把繁体转成简体或整理布局，返回的 `textUsage.safeForChangeSetSource=false` 表示不得复制其中任何 `previousText`、上下文或 scope 标记。若预演零命中诊断为 `DISPLAY_TEXT_USED_AS_CHANGE_SOURCE` 或 `CHANGE_TEXT_ENCODING_MISMATCH`，必须按诊断对同一路径重新 `--raw` 读取并重建 change-set；诊断只提供恢复路线，不会自动改字或跨编码写入。组成 change-set 后先运行 `pvf-change validate`；未知字段会直接报错，其 `agentHandoff` 明确要求把同路径多项改动留在同一个数组、连续第二轮使用 `baseline.applyManifest`。不要阅读执行器源码或把多项改动拆成多个临时新源。Workbench 先计算一个最终文件；彼此独立时优先先写结构再写文字，若后续结构删除明确依赖“完整中文先清空”的结果，则保留 change-set 数组顺序。无论顺序如何，同一文件的全部安全文字仍只追加一次字符串表、修改一次脚本，所有中间命中与最终文件都统一精确复查。若同一文件出现“已验证文字 → 普通结构替换 → 已验证文字”的混排，validate 会要求拆成累计下一轮，因为这会形成多个文字批次；不要把“参数块 + 中文说明”整个声明为 `verified-inline-text`。
- 若同一文件中的某条变化在临时核验前失败，整份文件仍原子停止。已经通过自身静态检查的其他变化返回 `FILE_CHANGE_BATCH_BLOCKED`，并在 `blockDetails.blockedByChangeId`、`blockedByCode` 和 `agentHandoff.sameFileBatchRecovery` 中指出真正阻断项；这表示临时往返尚未执行，不是这些合法变化缺少 `CN_TEXT_ROUNDTRIP_REQUIRED` 证明。先修正或移除阻断项，其余合法变化原样重试。
- 首期只开放已确认承载名称/说明的文件类型；`.co`、`.lst`、NUT 等逻辑或登记文件不会因为含 `[name]` 就获得中文写权限。
- `etc/titlebook.etc` 的 `[send postal]` 已作为路径受限的已确认可见邮件文字容器开放：只允许该 `.etc` 中的完整反引号邮件 token，并继续要求目标确认的 Cn/Tw 编码、精确命中、临时输出往返和客户端邮箱文字检查。其他文件出现同名标签不会获得权限。
- 这类预演必须先在隔离临时输出中真实写入，再由独立 TypeScript 解析器使用同一编码精确读回；还要证明既有字符串表条目未改变，并比较另一中文编码是否显示出更可信的原文。任一检查失败都不能生成 approval code，核验记录内部也会明确标记许可已收回，临时输出随后清理。
- 直接修改既有 `.str`、直接修改 StringLink 显示文本、部分中文 token、未声明精确数量的批量替换和无法无损编码的字符仍必须失败关闭；新增 `.str` 只能走 `localization-new-file`，声明目标确认的 `Cn/Tw`、同类 reference 和独立编码往返。无操作替换不应触发写入。
- 如果输出 PVF 出现 HTML 实体化、路径乱码或客户端道具名/描述/副本文本乱码，禁止继续部署该输出。
- 涉及中文字符串文件的部署验收必须包含客户端 UI 文本 smoke check。

## 客户端资源

### 用户保存的自动部署授权

用户可明确要求将“本机指定客户端每次先备份再部署”保存为持续授权。使用 `client-pvf preference --profile <name> --enable --authorize-persistent-deploy`；配置保存在工作台外的本机 profile 状态目录，绑定 profile 名称、客户端路径及真实路径、来源 PVF 路径，不能随便携工作台分发。未开启时仍默认禁止客户端写入。读取用 `client-pvf preference --profile <name>`，撤销用同命令加 `--disable`。

开启后，成功的 `pvf-change apply` 会自动匹配唯一授权 profile，并执行 `client-pvf auto-deploy`：内部仍生成绑定预览、核对累计链和输出、检查客户端及启动器进程、备份、原子替换和重新核对。跨对话不重复索要已保存的授权，也不要求用户重复声明程序已关闭；程序检查失败或检测到运行进程时停止。备份后、替换前再检查一次。部署失败保留独立成品并报告，可关闭游戏后重试 auto-deploy。授权不允许自动切换不连续修改链，不涵盖恢复操作、NPK/IMG/UI 或其他游戏资源。
用户明确要求本轮仅生成、不部署时，在 apply 命令增加 `--no-auto-deploy`；只跳过本轮自动部署，不撤销持续偏好。用户最新明确指令优先于保存的偏好。

这条显式例外允许在客户端 `PVF-Backups/<旧版本SHA256>/sha256/<旧版本SHA256>.Script.pvf` 创建备份，每个不同旧版本单独目录；相同版本重新核验后复用，旧备份不覆盖。开启时先备份当前版本，失败则关闭该偏好。每次替换前必须确认当前版本备份完整且 SHA256 一致；路径及真实路径不得逃出客户端备份目录。profile 输出和部署核验记录仍在客户端外。下文逐次授权流程适用于未保存授权的客户端；“仅覆盖 Script.pvf”不排除这条路线明确授权的客户端备份副本。

### 活动列表成对介绍文字

`event/eventlistwindow.evt` 仅开放结构完整的 `[entry]` 内成对的介绍正文和成对单行标题：完整 `[event info]`（三个整数、活动代码、名称、两个八位日期、说明）与闭合 `[popupwindow design]`（同名 `[title]`、`[explain]` 完整文字及正整数宽度、可选既有链接字段、确认按钮）必须同时存在，两个正文必须相同，并在同一项精确计数替换中同步修改；标题也必须成对相同、同项同步修改且不含换行或标签括号。必须先按 token 解析完整结构，不能把文字或注释中的标签当作容器。

此例外仅允许非空普通说明；新旧正文不得是网址或包含尖括号标记，占位符数量与顺序保持。日期、活动代码、按钮、链接、其他 `.evt` 路径及通用 `[name]`/`[explain]` 不因此开放。仍使用 `verified-inline-text`、目标确认的 Cn/Tw、规则及原始 token 证明绑定、临时独立 PVF 往返、旧字符串表保全、正式独立输出与重新读回。部署后须检查活动文字显示、换行与溢出，静态核验不能证明窗口容量。

Script.pvf 内有资源引用，不代表客户端 ImagePacks2/NPK 资源完整。

修改客户端、写入 NPK、替换 IMG、部署资源包都需要单独授权。

把受控输出 `Script.pvf` 安装到测试客户端也属于单独授权，但可使用专门的 `workbench.bat client-pvf` 路线：

1. 只接受已成功读回并绑定最终输出 SHA256 的 `APPLY-MANIFEST.json`。
2. `preview` 只生成外部预览，不修改客户端；它绑定输出 PVF、profile 客户端根目录和客户端当前 `Script.pvf`。
多轮累积输出优先要求客户端当前 SHA256 等于本轮输入 SHA256（或已经等于候选输出）。客户端命中完整清单链中的更早祖先时，可在全部线性链接闭合后直接快进最终输出，并仍先备份客户端当前版本；任一清单缺失/漂移、输入输出不连续、锚点变化、链深度异常或客户端不在链上均停止。只有明确主动切换修改分支时，才可单独确认基线切换。
3. `deploy` 必须使用预览确认码，并确认客户端和启动器已关闭。
4. profile 的 source PVF 必须与 apply 清单记录的最初来源或受保护锚点一致。生成前，输入 PVF 与独立输出必须不同；部署时，受保护锚点、独立输出和客户端目标必须不同。最初来源可以就是客户端 `Script.pvf`，但只有其内容寻址备份已核对并成为受保护锚点后，才允许自动替换该客户端路径。
5. 替换前创建并核对客户端当前 PVF 的内容寻址备份；相同 SHA256 只存一份。
6. 部署后核对客户端目标 SHA256；恢复必须再次预览和确认，且客户端当前版本发生未知变化时停止。
7. 这项权限只覆盖 profile 客户端根目录的 `Script.pvf`，不包含 NPK、IMG、UI 或其他客户端文件。

既有同名空函数的保留仅适用于 direct-character-skill-use 和 direct-character-skill-proc：原文件已存在、所有重复函数体只含空白、全部声明文本逐个相同、数量及全文件函数顺序不变，而且不得列为修改函数。新增、删除、改动任何一个重复声明，或重复体含代码/注释，仍阻断。此例外只允许原样保留；原始字节保全与独立读回要求不变。


## 道具名称解除引用例外

用户明确改名时可用 verified-stringlink-detach，仅 .stk [name] 的单个完整 StringLink 转为独立文字，禁止修改共享文字表。明确目标编码、原始引用对绑定、既有字符串条目保全、临时独立往返及最终读回均必需。细节见 task-cards/stackable-stringlink-detach-controlled-change.zh-CN.md。此为上文 StringLink 只读规则的唯一名称解除引用例外，普通模式和其他位置继续阻断。

### 独立静态活动说明追加

用户明确要求独立活动说明时，`event/eventlistwindow.evt` 允许在完整文件末尾追加恰好一个静态说明条目。仅当末条为严格成对介绍格式、元数据为 -1/2/4 时，才可沿用其活动代码、日期和宽度；追加条目不得含链接、未知字段或激活逻辑，确认按钮为 1。新增标题和正文先用唯一的普通 ASCII 占位文字，再按成对文字路线本地化。完整原文必须逐字保留，非末尾修改、重复条目、旧标题复用、元数据变化全部阻断。结构预演仍需原始 token/旧字符串保全证明，正式独立输出后完整读回。此路线只证明数据结构闭合，重复静态编号在具体客户端的展示行为须通过活动列表与弹窗实机检查，不声称已验证活动激活语义。

## 明确的独立文字路线

未知标签不等于危险标签。用户明确指定的独立标量文字可使用 `verified-scalar-text`；具体结构、模式与验证步骤唯一归属 task-cards/pvf-scalar-text-controlled-change.zh-CN.md。它是独立的已登记结构路线，不放宽普通 verified-inline-text 的自动显示判断。运行含义未验证、占位符保留、目标编码、旧字符串与非目标 token 保全、临时往返及最终读回必须如实记录。现有受保护文件与结构化记录继续走各自路线。上文“未知基础标签停止”适用于普通自动文字模式，不否定显式标量路线。
