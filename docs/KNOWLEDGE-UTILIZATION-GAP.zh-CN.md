# 知识利用缺口反馈与修复指南

这份文档用于处理一种常见问题：工作台里可能已经有相关资料，但 Agent 在真实任务中没有主动找到、联想到或组合使用；也可能看起来像知识问题，实际是工具能力不足、安全规则正确阻断，或目标版本缺少证据。

用户不需要先判断是哪一种。只要描述实际经过，维护者负责复现、分类和修复。

## 以后怎么告诉 Agent

最简单的说法：

> 请先阅读 `docs/KNOWLEDGE-UTILIZATION-GAP.zh-CN.md`。我遇到一个疑似知识利用缺口：……

后面直接用自己的话描述即可。能提供多少就提供多少，不必填写技术术语。最有价值的信息是：

1. 当时对 Agent 说的原话或大意。
2. Agent 实际查了什么、给出了什么方案，或者停在了哪里。
3. 你后来提醒了哪个字段、文件、关联方向或操作。
4. 提醒以后，Agent 是否立刻就会做了。
5. 知道的话，附上目标 PVF、对象名称或数字 ID；不知道可以不填。
6. 是否允许只读调查、是否能做游戏内验证。没有单独授权时，不修改 PVF 或客户端。

不需要保存完整聊天记录。能够说明“原本不会，提醒什么以后才会”通常就足以开始调查。

## 可直接复制的反馈模板

```text
请先阅读 docs/KNOWLEDGE-UTILIZATION-GAP.zh-CN.md。

我遇到一个疑似知识利用缺口：
- 我当时想做：
- 我对 Agent 说了：
- Agent 实际做了或回答了：
- 我后来提醒了：
- 提醒后的变化：
- 目标 PVF / 对象（知道就填）：
- 是否可以只读调查：可以
- 是否可以游戏内验证：

请先判断它属于知识缺失、知识没有被找到、知识不会组合、工具限制，还是安全规则正确阻断。先只读复现；确认原因后再完善工作台并做相应回归测试。没有明确授权不要修改真实 PVF 或客户端。
```

模板不是表格作业。忘记某项或只记得大概现象，也可以直接反馈。

## 什么情况值得反馈

- 你不点名字段、文件或关联方向时，Agent 没有思路；点名后立即会了。
- Agent 找到了目标文件，却只看最显眼的一个字段，没有检查相关系统。
- 知识包明明收录了某项资料，Agent 仍反复扫描、猜路径或说没有资料。
- Agent 能解释单个词条，却不能把用户的体验语言转换成检查步骤。
- 同一种任务换一种自然说法，Agent 就进入了完全不同或明显错误的路线。
- Agent 给出的方案技术上能执行，但遗漏了重要依赖、影响范围或实机验证。
- Agent 声称“工作台不能做”，但你怀疑只是没有找到已经存在的能力。

以下现象不一定是缺口：

- Agent 因没有目标 PVF、对象身份或当前版本证据而暂时不下结论。
- 安全规则要求预演、独立输出、备份、读回或单独授权客户端操作。
- 某个字段的结构已经确认，但最终公式或游戏手感仍必须实机验证。
- Agent 给出较短回答，但关键对象、依赖、风险和验证都没有遗漏。

## 维护者如何判断原因

先保留用户原始说法，使用目标 PVF 做只读复现；不要先把正确字段写进提示词，否则会掩盖真实问题。然后把原因归入以下一种或多种：

1. **知识缺失或过时**：知识包没有结论，或者现有结论不适用于目标版本。
2. **路由缺口**：资料已经存在，但用户的自然语言没有把 Agent 带到正确任务卡或词典。
3. **组合方法缺口**：Agent 已经读到资料，却不知道一个体验目标需要联合检查哪些层次、按什么顺序排查。
4. **工具能力缺口**：思路正确，但工作台不能定位、读取、复制、预演或核验所需对象。
5. **证据或安全边界**：Agent 的停止本身正确，需要补的是解释、取样方案或实机验证，而不是放宽权限。
6. **测试缺口**：文档和能力看似齐全，但测试只验证了命令能运行，没有验证“不提示字段时 Agent 会不会主动使用”。

“提醒后立即会了”通常更接近路由或组合方法缺口；“提醒后仍然无法执行”更可能是知识、工具或证据缺口。这只是线索，必须以只读复现为准。

## 修复原则

1. 先证明缺口存在，再修改工作台；不要仅凭一次不理想回答就向根规则堆关键词。
2. 修最小的正确所有者：
   - 缺事实，补词典、索引或经过验收的知识结论；
   - 找不到事实，补最短路由；
   - 不会联合分析，补任务卡或流程；
   - 命令做不到，才修改工具能力；
   - 正确阻断，改进说明或验证路线，不放宽安全边界。
3. 根 `AGENTS.md` 只保留会影响第一条命令或关键分流的短规则，领域细节继续放在按需读取的知识文件中。
4. “相关”不等于“应该修改”。任务卡可以要求联合检查多个来源，但没有目标版本参照和实机依据时，不能武断推荐最佳数值层。
5. 默认只读复现。修改工作台不自动授权生成 PVF、覆盖源 PVF 或部署客户端。
6. 外部教程、报告和测试产物留在工作台外；只有短结论、字段边界和可执行方法进入纯净知识包。

## 回归验收

修复不能只检查文档是否存在。至少要验证：

- 测试提示使用用户原来的自然语言，不提前透露正确字段或文件。
- Agent 先按正确方式确认目标身份，再读取命中的短知识路线。
- Agent 能主动列出需要联合检查的主要层次，而不是只抓一个显眼字段。
- Agent 能区分已确认事实、候选解释和仍未解决的项目。
- 没有证据时不会虚构公式、最佳数值或跨版本结论。
- 没有写入授权时不修改 PVF 或客户端。
- 修改知识文件后重建并检查知识清单；修改 Agent 指引、安全路线或工具能力后，运行对应自测和发布门禁。
- 涉及 Agent 指引或安全路由时，发布前还要用全新发布暂存副本做真实外部 Agent 黑盒测试；外部测试不可用时明确保留未完成项，不能用内置自测冒充。

## 一个简短例子

用户说“让 APC 更耐打”，Agent 原本只看一个伤害或受击反应字段；用户点名 `[additional character status]` 和 `[character status rate]` 后，Agent 才会检查生命、物防、魔防和受击恢复。

这里不一定缺少字段资料。只读复现后若确认词典早已存在，真正要修的是“更耐打”到生存维度的路由，以及联合审阅两个面板块的任务方法。验收时应重新使用“更耐打”这句话，不能在测试提示中替 Agent 写出两个标签。

今后副本、任务、掉落、装备、技能或客户端资源遇到类似现象，也按同一方法处理。无需提前开展一次覆盖全领域的大改造；真实案例本身就是最有价值的测试题。
