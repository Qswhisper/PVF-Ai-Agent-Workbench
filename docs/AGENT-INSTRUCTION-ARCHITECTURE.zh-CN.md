# Agent 指令分层

状态：发布维护规则

## 目标

根指令是每次任务都会消耗的冷启动上下文，不是功能百科。应让 Agent 快速知道“先做什么、不能做什么、去哪里读取细节”，把具体格式和长流程留给按需路由文件与命令返回值。

体积上限由环境检查强制：

- `AGENTS.md`：不超过 24 KiB，推荐维持在 8–14 KiB。
- `.agents/skills/dnf-pvf-xpilot/SKILL.md`：不超过 8 KiB，推荐维持在 2–3 KiB。
- `agents/dnf-pvf-agent.md` 与 `agents/pvf-safety-rules.md`：各不超过 4 KiB，只作旧宿主兼容指针。

上限是防止回涨的护栏，不是必须填满的目标。

## 唯一归属

- `AGENTS.md`：Skill 之后的冷启动、第一条命令、全局不变量、短路由和维护检查。
- `knowledge-pack/safety/README.zh-CN.md`：写 PVF、中文编码、精确定位、连续输出和客户端部署的完整安全规则。
- `knowledge-pack/indexes/knowledge-index.json`：领域入口；任务卡、词典和流程文件拥有具体领域做法。
- `agentHandoff`：当前命令完成或阻断后唯一可靠的下一条命令、恢复路线和禁止绕路提示。
- `core/pvf-agent-core/cli/README.md`：命令示例。
- 发布清单和本文件：维护者的打包、体积和验证要求。
- `agents/` 下旧入口：只指向上述权威文件，不保存独立规则快照。

同一条详细规则不得在 AGENTS、Skill 和安全说明中各复制一份。根指令只保留足以防止错误分流的摘要，并链接到唯一归属。

## 不可下沉的内容

以下内容必须留在 `AGENTS.md`：

- Skill 必须先于 shell 或文件发现。
- 已知自然语言实体名称时，第一条 shell 是领域 `SearchName`；不能用 `check`、帮助或目录扫描抢在前面。
- 明确要求源文件前后不变时，指纹是路由首命令之后的下一条 Workbench 命令，并早于任何 `pvf-change`。
- 每次工具调用只运行一条裸 `workbench.bat` 命令，不预检已经明确的输入与输出目录。
- 默认只读、生成阶段不覆盖输入 PVF、不执行不可信内容、不默认写客户端；客户端来源路径只有在受保护备份锚点核验后才可单独授权部署。
- 精确只读快速路径的首命令和短路由。
- 原始读回、`validate`、预演、正式生成和最终读回的高层交接。
- 维护后必须运行的内测、发布门禁和真实 Agent 黑盒要求。

只读任务无需完整读入写入安全文件。Skill 只负责找到工作台和加载规则拥有者；根路由每主题只列一个首入口，扩展引用保留在深索引。维护可以检查源码，不受具体 PVF 修改任务的语法发现限制。

## 可以下沉的内容

- 字段级中文写入、上下文和 scope 的完整约束 → 安全说明。
- 客户端部署和恢复的完整绑定 → 安全说明与客户端部署流程。
- 各领域字段、依赖、地图、任务、物品和技能细节 → 知识路由。
- 命令示例和参数目录 → CLI README。
- 实现原理、测试夹具和发布历史 → docs、测试或更新日志。

## 受控写入能力契约

`core/pvf-agent-core/lib/controlled-write-capabilities.js` 是现有受控写入路线的机器可读注册表，也是 change-set 字段集合的运行时契约。它只描述已经实现并通过测试的路线，未知变化类型默认阻断；注册一项能力本身不得授予权限。

`config/write-policy.json` 只镜像注册表身份、默认阻断策略和完整能力 ID 集合，供环境检查发现策略漂移；它不能另行声明运行时能力。公开 `pvf-change-set.schema.json` 继续负责用户输入结构，运行时校验与自测必须检查 Schema 字段集合和能力契约一致。

预演结果必须写入解析后的 `capabilityId`，批准绑定必须包含该标识。正式生成在打开写入链路前重新从原始 change-set 解析能力，并拒绝缺失、未知或与预演不一致的标识。这样可把“允许什么、由谁规划、由谁写入、需要哪些证明”集中审计，同时保留各路线已有的字段级安全检查。

新增或调整能力时，应先明确唯一的 planner、writer、临时验证、最终读回和实机验证要求；同时更新注册表、Schema/运行时契约检查和闭集测试。不得仅修改策略 JSON、示例或说明文档来开放写入。

`core/pvf-agent-core/lib/controlled-execution-plan.js` 把已经通过字段级检查的结果投影为有顺序的执行计划。计划绑定每条变化的能力、planner、writer、状态、目标文件最终哈希、逐步变化哈希、定位范围和结构化组件；同一文件的最终哈希冲突会立即停止。预演清单保存该计划及其规范化 SHA256，批准绑定同时绑定计划 SHA256。

正式生成必须在任何写入前从当前源和同一 change-set 重新完成预检，生成相同的执行计划并逐项比较。替换类写入随后直接使用这次预检产生的计划对象，不得再读取并规划另一份隐式计划。临时往返证明、NUT/ANI 原始字节证明和最终独立读回仍是计划之外的附加硬条件，不能被“计划一致”替代。`config/write-policy.json` 的 `executionPlanContract` 只镜像这项机制，环境检查和受控写入自测负责发现漂移。

`core/pvf-agent-core/lib/verified-text-eligibility.js` 是完整可见文字 token 的统一资格分类器。它用一个封闭登记表描述直接可见标签、路径限定容器、从已知基础标签派生的 `.skl` ` ex` 家族，以及 `.dgn [tower dialog]` 严格记录；普通显示模式的未知标签、未知结构和受保护文件类型默认阻断；显式 verified-scalar-text 使用已登记的标量结构规则，不按标签词汇白名单授权，不证明游戏显示含义。分类结果统一携带规则 ID、策略 SHA256、目标路径、父标签和结构证据，不再由写入器中的零散白名单分别判断。

文字资格证明同时进入语义预检、临时往返写入证明、正式写入证明和 1.1 版受控执行计划。正式生成前重算的资格策略或命中证明只要与预演不同，就在任何写入前停止；写入器映射原始字符串 token 时还会再次核对相同规则路线。`verifiedTextEligibilityContract` 仍只是运行时登记表的机器镜像，不能单独增加规则或放宽权限。

## 修改检查表

1. 先确定规则唯一归属，再修改；不要先在 AGENTS 中追加一份“临时说明”。
2. 若根路由需要摘要，只写决定首命令或安全分流所需的最短内容。
3. 修改 Skill 或 AGENTS 后运行 `workbench.bat eval self-test`、`skill self-test` 和 `check`。
4. 修改安全写入交接后同时运行 `pvf-change self-test` 与 `fallback-self-test`。
5. 修改知识文件后重建并检查知识清单。
6. 发布前运行 Gate1、Gate2、Gate3，并使用全新会话做真实外部 Agent 黑盒；内置 eval 不能代替黑盒。
7. 黑盒必须确认首工具、首命令、指纹时序、无帮助/目录/check 绕路、错误安全停止、连续修改、生成后复查和源文件不变。

不为整理指令而放宽任何写权限，也不把真实 PVF、客户端、认证或测试输出放进工作台。
